# Практическое занятие №6: Веб-безопасность

# 🪩 Веб-приложение как объект защиты

Современное веб-приложение — это не одна HTML-страница, а распределённая система, в которой взаимодействуют несколько компонентов:

```text
Пользователь
    |
    v
Браузер
    |
 HTTPS
    |
    v
Веб-сервер / API
    |
    +--------> База данных
    |
    +--------> Файловое хранилище
    |
    +--------> Внешние сервисы
```

Каждый компонент имеет собственные границы доверия и собственные риски.

Браузер должен корректно обрабатывать недоверенный контент. Сервер должен проверять входные данные и права пользователя. База данных не должна получать запросы, сформированные конкатенацией непроверенных строк. Сеансовые идентификаторы не должны попадать в JavaScript при отсутствии необходимости.

Поэтому веб-безопасность нельзя свести к одному механизму вроде HTTPS.

---

# 🪩 HTTP и модель «запрос — ответ»

**HTTP (HyperText Transfer Protocol)** — прикладной протокол передачи данных между клиентом и сервером.

Типовой обмен выглядит так:

```text
Браузер                              Сервер
   |                                   |
   |---------- HTTP request ---------->|
   |                                   |
   |<--------- HTTP response ---------|
   |                                   |
```

Пример запроса:

```http
GET /profile HTTP/1.1
Host: example.com
User-Agent: Mozilla/5.0
Accept: text/html
```

Пример ответа:

```http
HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8
Content-Length: 1250

<html>
...
</html>
```

HTTP определяет структуру запросов и ответов, методы (`GET`, `POST`, `PUT`, `DELETE` и другие), заголовки и коды состояния.

---

# 🪩 Почему HTTP называют stateless

HTTP сам по себе не требует от сервера помнить предыдущие запросы клиента.

Например:

```text
Запрос 1:
GET /login

Запрос 2:
GET /profile
```

Без дополнительного механизма второй запрос не содержит информации о том, что пользователь уже проходил аутентификацию.

Именно поэтому веб-приложения используют cookies, токены и серверные сессии.

Важно различать: **HTTP является stateless на уровне протокола**, но веб-приложение может реализовать состояние поверх HTTP.

---

# 🪩 Что такое cookie

**Cookie** — небольшое значение, которое сервер передаёт браузеру, после чего браузер при выполнении подходящих условий автоматически отправляет его обратно серверу.

Сервер устанавливает cookie заголовком:

```http
Set-Cookie: session_id=4f8d2a91c7; Path=/; Secure; HttpOnly; SameSite=Lax
```

В последующих запросах браузер может отправить:

```http
Cookie: session_id=4f8d2a91c7
```

Таким образом, cookie становится механизмом связывания нескольких HTTP-запросов с одним пользовательским контекстом.

---

# 🪩 Зачем нужны cookies

Cookies применяются не только для авторизации.

## 5.1. Сессионная информация

Наиболее важный сценарий — хранение идентификатора пользовательской сессии.

После успешного входа сервер может сформировать случайный идентификатор:

```text
session_id = 8c2d7f96...
```

и связать его с серверной записью:

```text
8c2d7f96... -> user_id=42
```

Браузер хранит только идентификатор. Состояние авторизации находится на сервере.

## 5.2. Настройки интерфейса

Cookies могут использоваться для хранения некритичных предпочтений:

```text
language=ru
theme=dark
currency=RUB
```

## 5.3. Корзина и временные пользовательские данные

Некоторые приложения связывают корзину или другие временные данные с анонимной сессией ещё до входа пользователя.

## 5.4. Аналитика

Cookies могут применяться для измерения посещаемости и поведения пользователя. Такие механизмы требуют отдельного рассмотрения с точки зрения приватности и законодательства.

---

# 🪩 Cookie и сессия — не одно и то же

Cookie — объект, который хранит браузер.

Сессия — логическое состояние, которым управляет приложение.

Типовая архитектура:

```text
Браузер:
session_id=abc123
        |
        v
Сервер:
abc123 -> {
    user_id: 42,
    role: "student",
    expires: ...
}
```

Cookie содержит лишь идентификатор, а данные сессии остаются на стороне сервера.

Это безопаснее, чем хранить в cookie критичные значения вроде роли пользователя и доверять им без проверки.

---

# 🪩 Структура cookie

Общий вид:

```text
имя=значение; атрибут1; атрибут2=значение2; ...
```

Например:

```http
Set-Cookie: session_id=abc123; Path=/; Secure; HttpOnly; SameSite=Lax
```

Здесь `Path=/` задаёт область пути, `Secure` ограничивает передачу HTTPS, `HttpOnly` закрывает cookie от обычного JavaScript, а `SameSite=Lax` ограничивает межсайтовую отправку.

---

# 🪩 Domain и Path

Атрибут `Domain` определяет область домена, для которой cookie может отправляться. Если `Domain` не указан, cookie обычно привязывается к конкретному хосту, который её установил.

Атрибут `Path` ограничивает область пути:

```http
Set-Cookie: admin_session=abc; Path=/admin
```

Однако `Path` не является полноценным механизмом безопасности и не должен использоваться вместо серверной авторизации.

---

# 🪩 Session cookies и persistent cookies

Если cookie не содержит `Expires` или `Max-Age`, его обычно называют **session cookie**.

Пример:

```http
Set-Cookie: session_id=abc123; Secure; HttpOnly
```

Persistent cookie имеет заданное время жизни:

```http
Set-Cookie: language=ru; Max-Age=2592000
```

Срок жизни должен соответствовать назначению cookie.

---

# 🪩 Атрибут Secure

```http
Set-Cookie: session_id=abc123; Secure
```

`Secure` означает, что браузер должен передавать cookie только через защищённое HTTPS-соединение.

Для аутентификационных cookies этот атрибут должен быть стандартным выбором.

---

# 🪩 Атрибут HttpOnly

```http
Set-Cookie: session_id=abc123; HttpOnly
```

`HttpOnly` запрещает обычному JavaScript-коду страницы читать значение cookie через `document.cookie`.

Это особенно важно для session cookies. При XSS такой атрибут затрудняет прямую кражу cookie, но не устраняет саму XSS-уязвимость.

---

# 🪩 Атрибут SameSite

`SameSite` управляет тем, когда cookie разрешено отправлять в межсайтовом контексте.

```text
Strict
Lax
None
```

`Strict` — самый жёсткий режим. `Lax` — компромисс между безопасностью и совместимостью. `None` используется, когда cookie действительно должна работать в межсайтовом контексте, и обычно требует `Secure`.

---

# 🪩 First-party и third-party cookies

Упрощённо **first-party cookie** относится к сайту, с которым пользователь взаимодействует непосредственно.

**Third-party cookie** исторически использовалась сторонним доменом, встроенным в страницу другого сайта, например рекламной или аналитической системой.

Современные браузеры всё сильнее ограничивают межсайтовое отслеживание. Для разработчика важен принцип минимально необходимой области действия cookie.

---

# 🪩 Безопасный шаблон session cookie

Для типовой сессии можно стремиться к конфигурации:

```http
Set-Cookie: session_id=4f8d2a91c7; Path=/; Secure; HttpOnly; SameSite=Lax
```

На сервере идентификатор должен быть случайным и непредсказуемым, сессия должна иметь срок жизни, при входе желательно обновлять идентификатор, а после выхода — инвалидировать его.

---

# 🪩 Session hijacking

**Session hijacking** — получение злоумышленником действующего идентификатора пользовательской сессии.

Источники компрометации могут включать XSS, незашифрованный HTTP, утечки журналов, ошибки приложения или небезопасное хранение токенов.

Защита строится сочетанием:

```text
HTTPS
+
Secure
+
HttpOnly
+
SameSite
+
ограниченный срок жизни
+
ротация session_id
+
серверная инвалидизация
```

---

# 🪩 Cookie poisoning

Пользователь имеет возможность изменять многие cookies в собственном браузере.

Поэтому сервер не должен доверять критичным значениям, полученным из cookie, без проверки.

Плохая конструкция:

```text
role=admin
price=1
is_paid=true
```

если сервер воспринимает эти данные как истину.

Надёжнее хранить только идентификатор сессии, а реальные права и бизнес-данные — на сервере.

---

# 🪩 Проблема незашифрованного HTTP

HTTP сам по себе не обеспечивает криптографическую защиту канала.

Если пользователь отправляет:

```http
POST /login HTTP/1.1
Host: example.com
Content-Type: application/x-www-form-urlencoded

username=alice&password=secret
```

по незашифрованному соединению, данные передаются без TLS-защиты.

Проблема касается не только паролей, но и session cookies, форм, URL-параметров, API-запросов и ответов сервера.

---

# 🪩 Что такое HTTPS

**HTTPS** — HTTP поверх защищённого соединения TLS.

Упрощённо:

```text
HTTP + TLS = HTTPS
```

TLS обеспечивает три ключевых свойства:

1. конфиденциальность;
2. целостность;
3. аутентификацию сервера.

Важно: TLS защищает соединение, но не исправляет ошибки приложения.

---

# 🪩 SSL и TLS

Исторически TLS развился из SSL. Устаревшие версии SSL и ранние версии TLS не должны использоваться в современных системах.

Практически ориентироваться следует на:

```text
TLS 1.2
TLS 1.3
```

Термин «SSL-сертификат» до сих пор часто используется, хотя технически корректнее говорить о TLS/X.509-сертификате.

---

# 🪩 TLS Handshake

Упрощённая логика TLS 1.3:

```text
Клиент                          Сервер
  |                               |
  |-------- ClientHello --------->|
  |                               |
  |<------- ServerHello ----------|
  |<------- Certificate ----------|
  |<----- CertificateVerify ------|
  |<--------- Finished -----------|
  |                               |
  |---------- Finished ---------->|
  |                               |
  |====== защищённый трафик ======|
```

Во время handshake стороны согласуют параметры, формируют общий секрет и проверяют подлинность сервера.

---

# 🪩 Гибридная криптография в TLS

После согласования ключевого материала трафик защищается быстрыми симметричными AEAD-алгоритмами.

Упрощённо:

```text
ECDHE + цифровая подпись
        |
        v
согласование секретов
        |
        v
сеансовые ключи
        |
        v
AES-GCM / ChaCha20-Poly1305
        |
        v
защищённый HTTP-трафик
```

---

# 🪩 Forward Secrecy

Современные TLS-соединения используют эфемерное согласование ключей, например ECDHE.

**Forward Secrecy** означает, что компрометация долговременного закрытого ключа сервера в будущем не должна автоматически раскрывать ранее записанные сессии.

---

# 🪩 X.509-сертификат

X.509-сертификат связывает открытый ключ с идентификатором, например доменным именем.

Он содержит сведения о владельце, издателе, сроке действия, открытом ключе, Subject Alternative Name и цифровой подписи.

Сертификат является публичным документом.

**Закрытого ключа сервера в сертификате нет.**

---

# 🪩 Цепочка доверия

Обычно конечный сертификат сайта подписывается промежуточным удостоверяющим центром, а тот связан с корневым CA.

```text
Root CA
   |
   v
Intermediate CA
   |
   v
example.com
```

Браузер доверяет корневым сертификатам из доверенного хранилища и проверяет путь от сайта до доверенного корня.

---

# 🪩 Проверка доменного имени

Современный браузер проверяет, что запрошенное имя присутствует в `Subject Alternative Name`.

Если сертификат выдан для другого домена, браузер должен показать ошибку.

---

# 🪩 DV, OV и EV

**DV** подтверждает контроль над доменом.

**OV** включает дополнительные проверки организации.

**EV** исторически предполагал более строгую юридическую проверку.

С точки зрения криптографической защиты канала это не означает разную «силу шифрования». Различается прежде всего объём проверяемой идентификационной информации.

---

# 🪩 Wildcard и SAN-сертификаты

Wildcard:

```text
*.example.com
```

может покрывать поддомены одного уровня, например `api.example.com`, но не обязательно покрывает `example.com`.

SAN-сертификат может включать несколько разных имён.

---

# 🪩 HSTS

**HSTS (HTTP Strict Transport Security)** сообщает браузеру, что сайт должен открываться только через HTTPS.

```http
Strict-Transport-Security: max-age=31536000; includeSubDomains
```

Это снижает риск случайного перехода на HTTP после того, как браузер уже получил политику HSTS.

---

# 🪩 HTTPS не означает «сайт безопасен»

HTTPS означает, что соединение с указанным доменом защищено TLS.

Он не гарантирует, что приложение не содержит XSS, SQL Injection или ошибок авторизации, и не доказывает добросовестность самого сайта.

Фишинговый домен тоже может иметь корректный TLS-сертификат для собственного имени.

---

# 🪩 Основные угрозы веб-приложениям

В рамках занятия рассматриваются четыре базовых класса:

| Угроза | Основная проблема |
|---|---|
| XSS | выполнение недоверенного скрипта в браузере |
| CSRF | нежелательное действие от имени авторизованного пользователя |
| SQL Injection | смешивание данных и структуры SQL-запроса |
| Clickjacking | скрытое навязывание пользовательского клика |


# 🪩 XSS

**Cross-Site Scripting (XSS)** — класс уязвимостей, при которых недоверенные данные попадают в страницу таким образом, что браузер интерпретирует их как исполняемый код.

Безопасный учебный пример:

```html
<script>alert("XSS demo")</script>
```

Такой пример подходит для локального учебного стенда и показывает сам принцип без кражи данных.

Главная проблема XSS заключается в нарушении границы между данными пользователя и кодом страницы.

---

# 🪩 Reflected XSS

При reflected XSS недоверенное значение приходит в запросе и сразу включается в ответ.

Например, приложение формирует HTML:

```html
<h1>Результаты поиска: USER_INPUT</h1>
```

Если `USER_INPUT` вставляется без корректного экранирования, браузер может интерпретировать содержимое не как текст.

Правильный принцип:

> пользовательский ввод должен оставаться данными и не превращаться в исполняемый код.

---

# 🪩 Stored XSS

При stored XSS опасное значение сохраняется на сервере:

```text
комментарий
профиль
описание
сообщение
```

а затем возвращается другим пользователям.

Такая уязвимость особенно опасна, потому что вредоносный контент может автоматически затрагивать множество посетителей.

---

# 🪩 DOM-based XSS

DOM-based XSS возникает, когда проблема находится в клиентском JavaScript.

Опасный подход:

```javascript
element.innerHTML = userInput;
```

Если требуется вывести текст, предпочтительнее:

```javascript
element.textContent = userInput;
```

При этом `textContent` не является универсальным решением для всех возможных контекстов. Для HTML, URL, атрибутов, JavaScript и CSS применяются разные правила безопасного вывода.

---

# 🪩 Защита от XSS

Основные меры:

**Контекстное экранирование.** Данные кодируются с учётом того, куда они вставляются.

**Шаблонизаторы с autoescape.** Современные шаблонизаторы уменьшают вероятность случайной вставки необработанного HTML.

**Безопасные DOM API.** Следует предпочитать `textContent`, `createTextNode` и другие безопасные методы там, где нужен обычный текст.

**Content Security Policy.** CSP ограничивает источники исполняемого контента.

**HttpOnly.** Снижает риск прямой кражи session cookie через JavaScript.

**Отказ от опасных конструкций.** Без необходимости не следует использовать `eval`, небезопасный `innerHTML` и динамическое выполнение строкового кода.

---

# 🪩 Content Security Policy

CSP задаётся HTTP-заголовком.

Пример базовой политики:

```http
Content-Security-Policy: default-src 'self'; script-src 'self'
```

Такая политика разрешает ресурсы и скрипты только с текущего origin.

Более строгие политики могут использовать nonce или hashes для разрешения конкретных скриптов.

CSP является дополнительным барьером, но не заменяет корректную обработку пользовательского ввода.

---

# 🪩 CSRF

**Cross-Site Request Forgery (CSRF)** — атака, при которой браузер авторизованного пользователя вынуждают отправить нежелательный запрос на другой сайт.

Ключевой момент: браузер может автоматически приложить session cookies.

Сценарий:

```text
1. Пользователь вошёл в bank.example
2. В браузере есть session cookie
3. Пользователь открывает другой сайт
4. Тот инициирует запрос к bank.example
5. Браузер может приложить cookie
```

Если сервер не отличает легитимный запрос от подделанного, может выполниться нежелательное действие.

---

# 🪩 CSRF-token

Классическая защита — непредсказуемый токен, связанный с пользовательской сессией.

```html
<form method="POST" action="/profile/email">
    <input type="hidden" name="csrf_token" value="RANDOM_TOKEN">
    <input type="email" name="email">
    <button type="submit">Сохранить</button>
</form>
```

Сервер проверяет, что токен присутствует и соответствует ожидаемому значению.

---

# 🪩 SameSite как защита от CSRF

Правильно выбранный `SameSite` снижает вероятность автоматической отправки session cookie в межсайтовом контексте.

Например:

```http
Set-Cookie: session_id=abc; Secure; HttpOnly; SameSite=Lax
```

Однако SameSite не отменяет необходимость проектировать защиту критичных операций осознанно.

---

# 🪩 Origin и Referer

Для чувствительных запросов сервер может дополнительно проверять:

```http
Origin
Referer
```

Например, ожидать:

```text
Origin: https://app.example.com
```

Такая проверка может быть дополнительным барьером вместе с CSRF-token и SameSite.

---

# 🪩 SQL Injection

**SQL Injection** возникает, когда внешние данные смешиваются со структурой SQL-запроса.

Плохой пример:

```python
query = "SELECT * FROM users WHERE username = '" + username + "'"
```

Проблема заключается не в конкретном SQL-синтаксисе, а в смешивании данных пользователя и команд SQL.

---

# 🪩 Параметризованные запросы

Основная защита — отделить SQL-код от значений.

Пример для SQLite:

```python
cursor.execute(
    "SELECT id, username FROM users WHERE username = ?",
    (username,)
)
```

Для других драйверов синтаксис placeholder может отличаться.

Важно использовать штатный механизм параметров библиотеки, а не вручную экранировать SQL-строки.

---

# 🪩 ORM не отменяет необходимость думать

ORM часто снижает риск SQL Injection, поскольку обычные операции автоматически параметризуются.

Но raw-запросы могут снова создать проблему.

Рискованная идея:

```python
raw_sql = f"SELECT * FROM users WHERE name = '{name}'"
```

Даже при использовании ORM правило остаётся прежним: пользовательские значения не должны становиться частью SQL-кода через конкатенацию или форматирование строк.

---

# 🪩 Валидация и параметризация

Валидация проверяет бизнес-правила:

```text
возраст должен быть числом
username ограничен по длине
email должен иметь ожидаемый формат
```

Параметризация защищает границу SQL-кода и данных.

Эти меры дополняют друг друга и не являются взаимозаменяемыми.

---

# 🪩 Принцип наименьших привилегий для БД

Учётная запись приложения не должна обладать административными правами без необходимости.

Например, обычному веб-приложению не нужны права:

```text
DROP DATABASE
CREATE USER
ALTER SYSTEM
```

Ограниченные права уменьшают последствия возможной ошибки.

---

# 🪩 Clickjacking

**Clickjacking** — атака на пользовательский интерфейс, при которой пользователя заставляют нажать на скрытый или замаскированный элемент другого сайта.

Типовой принцип:

```text
видимая кнопка
+
невидимый iframe
```

Пользователь думает, что взаимодействует с одним интерфейсом, а фактически нажимает на другой.

---

# 🪩 Защита от Clickjacking

Исторически используется:

```http
X-Frame-Options: DENY
```

или:

```http
X-Frame-Options: SAMEORIGIN
```

Современный механизм CSP:

```http
Content-Security-Policy: frame-ancestors 'none'
```

или:

```http
Content-Security-Policy: frame-ancestors 'self'
```

`frame-ancestors` позволяет гибко управлять тем, кто имеет право встраивать страницу.

---

# 🪩 Аутентификация и авторизация

В веб-безопасности необходимо различать:

**Аутентификация** — кто вы?

**Авторизация** — что вам разрешено?

Пользователь может быть успешно аутентифицирован, но не иметь прав администратора.

Поэтому сервер обязан проверять полномочия для каждой чувствительной операции.

---

# 🪩 Нельзя доверять клиенту

HTML, JavaScript, cookies, query parameters, hidden inputs и JSON находятся под контролем пользователя.

Поэтому проверки только в браузере улучшают удобство, но не являются границей безопасности.

Все критичные правила должны проверяться на сервере.

---

# 🪩 Безопасность паролей

Пароли пользователей нельзя хранить:

```text
в открытом виде
с обычным обратимым шифрованием
в виде простого SHA-256(password)
```

Для хранения применяются специализированные password hashing алгоритмы:

```text
Argon2id
scrypt
bcrypt
PBKDF2
```

Система хранит результат password hashing и параметры алгоритма.

---

# 🪩 MFA

**Многофакторная аутентификация** снижает риск компрометации учётной записи при утечке одного пароля.

Могут использоваться:

- TOTP;
- аппаратные ключи;
- passkeys / WebAuthn;
- push-подтверждение;
- резервные коды.

SMS-код лучше одного пароля, но имеет собственные ограничения.

---

# 🪩 Безопасные HTTP-заголовки

Помимо CSP, HSTS и защиты от framing, приложения используют дополнительные заголовки.

Например:

```http
X-Content-Type-Options: nosniff
```

и:

```http
Referrer-Policy: strict-origin-when-cross-origin
```

Для реального приложения набор заголовков должен подбираться под архитектуру.

---

# 🪩 Same-Origin Policy

Одной из фундаментальных защит браузера является **Same-Origin Policy**.

Origin определяется сочетанием:

```text
scheme + host + port
```

Например:

```text
https://example.com:443
```

и:

```text
https://api.example.com:443
```

имеют разные origins.

Same-Origin Policy ограничивает доступ одного происхождения к данным другого.

---

# 🪩 CORS

**CORS (Cross-Origin Resource Sharing)** определяет, каким origin браузер разрешает читать ответы другого origin через JavaScript.

Например:

```http
Access-Control-Allow-Origin: https://app.example.com
```

Важно:

> CORS — браузерный механизм, а не полноценная серверная авторизация.

API всё равно должно проверять пользователя и его права.

---

# 🪩 Defense in Depth

Рассмотрим набор:

```text
TLS
+
Secure cookie
+
HttpOnly
+
SameSite
+
CSP
+
CSRF token
+
parameterized SQL
+
authorization checks
```

Каждый механизм закрывает свою часть угроз.

Это и есть **defense in depth** — эшелонированная защита.

# Практическое занятие №14: Тестирование механизмов защиты и анализ результатов

## ⚙️ Что такое тестирование безопасности

**Тестирование безопасности** — проверка того, сохраняет ли система требуемые защитные свойства при некорректных, неожиданных или потенциально опасных действиях пользователя.

В рамках курсовой работы тестирование проводится только на собственной системе или специально созданном учебном стенде.

Задача состоит не в поиске максимального количества способов «взлома», а в проверке корректности тех механизмов защиты, которые были заложены в проект.

## ⚙️ Формирование тест-кейсов

Для каждого требования безопасности следует подготовить отдельный тест-кейс.

Рекомендуемая структура:

| Поле | Содержание |
|---|---|
| ID | SEC-T01 |
| Проверяемое требование | SEC-01 |
| Предусловия | Пользователь авторизован |
| Действия | Изменить идентификатор объекта в запросе |
| Ожидаемый результат | Доступ запрещён |
| Фактический результат |  |
| Статус | PASS / FAIL |

## ⚙️ Позитивные и негативные сценарии

Позитивный тест подтверждает, что разрешённое действие выполняется корректно.

Негативный тест показывает, что запрещённое действие блокируется.

Пример:

```text
Позитивный сценарий:
владелец документа открывает свой документ → доступ разрешён

Негативный сценарий:
другой пользователь пытается открыть тот же документ → доступ запрещён
```

Оба сценария важны: система должна не только блокировать опасные действия, но и не мешать нормальной работе.

## ⚙️ Проверка аутентификации и авторизации

Если проект использует пользователей и роли, необходимо проверить:

- вход с корректными учётными данными;
- вход с неверным паролем;
- доступ без аутентификации;
- доступ обычного пользователя к административным функциям;
- доступ одного пользователя к данным другого;
- завершение пользовательской сессии.

## ⚙️ Проверка работы с пользовательским вводом

Если система принимает параметры от пользователя, необходимо убедиться, что ввод не способен изменить структуру SQL-запроса, HTML-документа или другой управляющей конструкции.

Проверяется общий принцип:

```text
данные остаются данными
```

Например, пользовательский ввод не должен превращаться в исполняемый HTML или SQL-код.

## ⚙️ Проверка конфиденциальности

В зависимости от темы можно проверить:

```text
пароли отсутствуют в БД в открытом виде;
секреты отсутствуют в репозитории;
чужие данные не возвращаются через API;
защищённые файлы невозможно прочитать без ключа;
конфиденциальные параметры не попадают в журналы.
```

## ⚙️ Проверка целостности

Если в проекте реализован контроль целостности, полезен следующий сценарий:

```text
1. создать корректный объект;
2. сохранить контрольное значение;
3. изменить защищаемые данные;
4. повторно выполнить проверку;
5. система должна обнаружить изменение.
```

## ⚙️ Проверка журналирования

Если система ведёт аудит, необходимо проверить регистрацию критичных событий:

- успешный вход;
- неудачная аутентификация;
- изменение критичных данных;
- запрещённый доступ;
- административное действие.

Журнал не должен содержать пароли, секреты и приватные ключи.

## ⚙️ Автоматизированные тесты

Часть проверок рекомендуется автоматизировать.

Пример:

```python
def test_regular_user_cannot_access_admin(client, user_token):
    response = client.get(
        "/admin",
        headers={"Authorization": f"Bearer {user_token}"}
    )
    assert response.status_code in (401, 403)
```

Автоматические тесты позволяют повторить проверку после изменения кода.

## ⚙️ Анализ результатов

После тестирования необходимо не только указать `PASS` или `FAIL`, но и объяснить результат.

Пример:

> В ходе тестирования установлено, что проверка владельца объекта первоначально выполнялась только на клиентской стороне. После добавления серверной проверки попытка обращения к чужому объекту завершается отказом. Повторное тестирование подтвердило выполнение требования SEC-04.

## ⚙️ Подтверждающие материалы

Результаты рекомендуется подтверждать:

- скриншотами;
- журналами событий;
- выводом консоли;
- результатами автотестов;
- содержимым БД;
- HTTP-ответами;
- дополнительными схемами и таблицами.

Каждая иллюстрация должна сопровождаться пояснением, что именно она подтверждает.

5. повторно выполнить тесты;

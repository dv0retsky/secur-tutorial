# Практическое занятие №10: Методические указания к выполнению курсовой работы по дисциплине «Методы защиты информации»

## ⚜️ Место курсовой работы в структуре семестра

Семестр включает **16 практических занятий**. Первые девять занятий посвящены изучению основных подходов к защите информации и практической работе с отдельными механизмами безопасности. Начиная с десятого занятия полученные знания объединяются в самостоятельный проект.

В ходе курсовой работы студент проходит полный цикл разработки защищённой информационной системы:

**анализ задачи → определение угроз → формирование требований → выбор методов защиты → программная реализация → тестирование → оформление результатов → защита.**

Работа выполняется поэтапно. Каждая последующая неделя должна опираться на результаты предыдущей, поэтому откладывать основную разработку на последние занятия не следует.

## ⚜️ Общая задача курсовой работы

Курсовая работа по дисциплине «Методы защиты информации» должна быть связана с проектированием, разработкой или исследованием **программных механизмов обеспечения информационной безопасности**.

Итогом работы должен стать программный продукт, модуль, прототип, программно-аналитический инструмент или учебный стенд, в котором реализованы конкретные методы защиты информации.

Курсовая работа должна позволять ответить на четыре основных вопроса:

1. **Что защищается?**
2. **От каких угроз необходимо защищать систему?**
3. **Какие методы защиты выбраны и почему?**
4. **Каким образом проверено, что реализованные механизмы действительно работают?**

Если один из этих вопросов остаётся без ответа, работа считается методически незавершённой.

## ⚜️ Требования к теме курсовой работы

Тема должна быть связана не просто с разработкой информационной системы, а именно с обеспечением её безопасности.

Например, тема:

> «Разработка веб-приложения для хранения заметок»

слишком общая, потому что из неё не видно, какие задачи защиты информации решаются.

Более корректная формулировка:

> «Разработка защищённого веб-приложения для хранения пользовательских заметок с аутентификацией, разграничением доступа и защитой от типовых веб-уязвимостей».

Хорошая формулировка темы обычно содержит три компонента:

**объект разработки + защищаемое свойство или задача + применяемые методы защиты.**

### Возможные направления курсовых работ

В качестве объекта разработки могут быть выбраны:

- защищённое веб-приложение;
- система хранения конфиденциальных файлов;
- модуль шифрования и контроля целостности данных;
- система безопасной регистрации и аутентификации пользователей;
- защищённый REST API;
- система разграничения прав доступа;
- программный модуль журналирования событий безопасности;
- система контроля целостности файлов;
- защищённый файловый обмен;
- менеджер паролей;
- инструмент анализа журналов событий;
- учебный стенд для исследования типовых уязвимостей;
- система резервного копирования с контролем целостности;
- программный модуль безопасного хранения секретов;
- средство анализа параметров безопасности локальной сети.

Студент может предложить собственную тему, если в ней присутствует содержательная задача по защите информации и предполагается программная реализация.

## ⚜️ Объект защиты и защищаемые свойства

На раннем этапе необходимо определить, **какие именно информационные ресурсы являются ценными**.

Объектами защиты могут выступать:

- учётные записи пользователей;
- пароли;
- персональные данные;
- файлы;
- документы;
- сообщения;
- параметры конфигурации;
- токены доступа;
- ключи;
- журналы событий;
- данные в базе данных;
- сетевые запросы;
- административные функции приложения.

При проектировании рекомендуется опираться на классическую триаду информационной безопасности:

- **конфиденциальность** — информация не должна быть доступна посторонним;
- **целостность** — данные не должны быть незаметно изменены;
- **доступность** — система и данные должны оставаться доступными для легитимных пользователей.

Дополнительно в работе могут рассматриваться подлинность, неотказуемость, авторизация, аудит действий и контроль доступа.

Пример связи между ресурсом и механизмом защиты:

| Ресурс | Возможное нарушение | Требуемое свойство | Пример метода защиты |
|---|---|---|---|
| Пароль пользователя | Получение пароля из БД | Конфиденциальность | Хеширование пароля |
| Файл | Чтение посторонним | Конфиденциальность | Шифрование |
| Файл | Незаметное изменение | Целостность | MAC / AEAD |
| Учётная запись | Вход другим пользователем | Подлинность | Аутентификация |
| Административная функция | Выполнение обычным пользователем | Авторизация | RBAC / ACL |
| Сессия | Перехват идентификатора | Конфиденциальность | Secure, HttpOnly, SameSite |

## ⚜️ Анализ угроз

До выбора методов защиты необходимо определить, от каких действий или событий должна защищаться система.

**Угроза информационной безопасности** — потенциальная причина нарушения конфиденциальности, целостности или доступности информации.

**Уязвимость** — слабое место системы, которое может быть использовано для реализации угрозы.

Например:

> Угроза — несанкционированный доступ к административной функции.  
> Уязвимость — сервер не проверяет роль пользователя.  
> Метод защиты — проверка прав доступа на стороне сервера.

Для курсовой работы рекомендуется определить **не менее пяти актуальных угроз**, непосредственно относящихся к проектируемой системе.

Удобная форма представления:

| № | Защищаемый ресурс | Угроза | Причина / уязвимость | Возможные последствия | Метод защиты |
|---:|---|---|---|---|---|
| 1 |  |  |  |  |  |
| 2 |  |  |  |  |  |
| 3 |  |  |  |  |  |
| 4 |  |  |  |  |  |
| 5 |  |  |  |  |  |

Важно, чтобы угрозы соответствовали конкретной системе. Например, SQL Injection актуальна для приложения, формирующего SQL-запросы на основании пользовательского ввода, но не обязательно имеет смысл для автономной утилиты шифрования файлов.

---

## ⚜️ Модель нарушителя

Для обоснования защиты необходимо кратко определить, какими возможностями обладает предполагаемый нарушитель.

В зависимости от темы можно рассматривать:

- внешнего пользователя, не прошедшего аутентификацию;
- легитимного пользователя с ограниченными правами;
- пользователя, пытающегося получить доступ к чужим данным;
- нарушителя, получившего копию базы данных;
- нарушителя, имеющего доступ к локальным файлам программы;
- сетевого нарушителя, способного наблюдать или изменять трафик в пределах выбранной модели.

Модель нарушителя должна быть реалистичной. Не требуется считать, что нарушитель способен делать абсолютно всё. Напротив, важно определить его реальные возможности и уже на их основе выбрать достаточные меры защиты.

## ⚜️ Требования к программной части

Курсовая работа обязательно должна содержать **работоспособную программную реализацию**.

Минимальный результат — прототип, который можно запустить и использовать для демонстрации заявленных методов защиты.

Рекомендуется реализовать **не менее трёх взаимосвязанных механизмов защиты**, относящихся к разным аспектам безопасности.

Например, для веб-приложения это могут быть:

1. безопасное хранение паролей;
2. параметризованные SQL-запросы;
3. защита от XSS;
4. защита от CSRF;
5. разграничение прав доступа;
6. безопасные настройки cookie;
7. журналирование событий безопасности.

Для системы защищённого хранения файлов:

1. шифрование содержимого;
2. безопасное формирование или хранение ключа;
3. контроль целостности;
4. аутентификация;
5. разграничение доступа;
6. журналирование операций.

Не следует оценивать проект по количеству защитных функций. Лучше реализовать несколько механизмов корректно, чем добавить большое количество формальных и несвязанных мер.

## ⚜️ Связь «угроза — требование — механизм»

Выбор метода защиты должен быть обоснован.

Недостаточно написать:

> «Для безопасности используется шифрование».

Необходимо объяснить, **какие данные шифруются, от какой угрозы это защищает, где применяется шифрование, как управляются ключи и каким способом проверяется результат**.

Рекомендуется строить обоснование в следующем порядке:

```text
защищаемый ресурс
        ↓
угроза
        ↓
уязвимость
        ↓
требование безопасности
        ↓
выбранный метод защиты
        ↓
программная реализация
        ↓
экспериментальная проверка
```

Пример:

```text
пароль пользователя
        ↓
компрометация базы данных
        ↓
пароли хранятся в открытом виде
        ↓
пароль не должен храниться в восстанавливаемой форме
        ↓
Argon2id / bcrypt / scrypt
        ↓
хранение хеша и соли
        ↓
проверка содержимого БД и корректности аутентификации
```

## ⚜️ Требования к структуре проекта

Программная часть должна быть воспроизводимой: преподаватель должен иметь возможность получить исходный код, установить зависимости и запустить приложение по инструкции.

Пример структуры репозитория:

```text
course-project/
├── README.md
├── requirements.txt / pyproject.toml / package.json
├── src/
├── tests/
├── docs/
├── screenshots/
└── report/
```

Структура может отличаться, но в проекте обязательно должны присутствовать:

- исходный код;
- файл зависимостей;
- инструкция по запуску;
- описание основных механизмов защиты;
- тестовые данные или процедура их создания;
- описание проверки работоспособности проекта.

В репозитории не должно быть реальных паролей, токенов, API-ключей, приватных ключей и иных секретов. Такие значения необходимо задавать через переменные окружения, отдельные конфигурационные файлы, исключённые из репозитория, или генерировать при первом запуске.

## ⚜️ Требования к исходному коду

Код должен быть понятным, воспроизводимым и соответствовать заявленной архитектуре.

Особое внимание следует уделять следующим принципам:

**Безопасность по умолчанию.** Потенциально опасная функциональность не должна включаться автоматически.

**Минимальные привилегии.** Компонент получает только те права, которые действительно необходимы ему для работы.

**Разделение данных и управляющих конструкций.** Например, пользовательский ввод не должен напрямую формировать SQL-запрос.

**Использование проверенных библиотек.** Самостоятельно реализовывать криптографические алгоритмы в курсовой работе не требуется, если сама разработка криптоалгоритма не является предметом исследования.

**Корректная обработка ошибок.** Пользователь не должен получать внутренние трассировки, строки подключения, секреты и другие служебные сведения.

---

## ⚜️ Требования к экспериментальной проверке

Курсовая работа должна показать, что реализованный механизм защиты не просто присутствует в коде, а действительно выполняет заявленную функцию.

Для каждого основного требования необходимо сформировать проверочный сценарий.

Например:

| Требование | Проверка | Ожидаемый результат |
|---|---|---|
| Пользователь не должен видеть чужие данные | Обратиться к чужому объекту | Доступ запрещён |
| Пароль не хранится открыто | Просмотреть запись в БД | Открытый пароль отсутствует |
| SQL Injection не должна изменять структуру запроса | Передать специальное значение в форму | Значение обрабатывается как данные |
| XSS-код не должен выполняться | Передать HTML/JavaScript в поле ввода | Ввод отображается как текст |
| Изменённый файл должен быть обнаружен | Изменить защищённый файл | Проверка целостности завершается ошибкой |

Желательно показывать состояние системы **до и после применения защиты**. Такой подход наглядно демонстрирует назначение реализованного механизма.

- схема криптографической обработки данных.

Для проектов по информационной безопасности особенно полезно показывать **границы доверия** и направления передачи данных.

Пример:

```text
[Пользователь]
      |
      | недоверенный ввод
      v
[Веб-приложение]
      |
      | параметризованные запросы
      v
[База данных]
```

## ⚜️ Требования к демонстрации проекта

На защите необходимо показать программный продукт в работе.

Предпочтительная логика демонстрации:

```text
1. запуск системы;
2. нормальный пользовательский сценарий;
3. демонстрация угрозы или некорректного сценария;
4. срабатывание реализованного механизма защиты;
5. подтверждение результата тестом или журналом событий.
```

Пример для веб-приложения:

```text
вход обычного пользователя
→
попытка доступа к административному разделу
→
отказ в доступе
```

Пример для программы защиты файлов:

```text
исходный файл
→
шифрование
→
проверка невозможности чтения
→
расшифрование
→
изменение зашифрованного контейнера
→
ошибка проверки целостности
```

## ⚜️ Критерии оценивания

При оценивании важна не только работоспособность программы, но и обоснованность проектных решений.

| Критерий | Доля |
|---|---:|
| Постановка задачи и актуальность | 10% |
| Анализ угроз и требований | 15% |
| Обоснование методов защиты | 15% |
| Качество программной реализации | 25% |
| Экспериментальная проверка | 15% |
| Качество пояснительной записки | 10% |
| Защита, демонстрация и ответы на вопросы | 10% |
| **Итого** | **100%** |

Высокая оценка предполагает, что в работе прослеживается единая цепочка:

**угроза → требование → метод защиты → реализация → проверка → результат.**

## ⚜️ Типичные ошибки

Наиболее распространённая проблема — формальный подход, когда в отчёте перечислены методы защиты, но не объясняется, зачем они нужны конкретной системе.

Также снижают качество работы:

- отсутствие анализа угроз;
- минимальная программная часть при большом теоретическом разделе;
- отсутствие тестирования;
- методы защиты, не связанные с выявленными угрозами;
- хранение секретов непосредственно в исходном коде;
- использование устаревших механизмов без объяснения;
- отсутствие инструкции по запуску;
- проект, который запускается только на компьютере автора;
- несоответствие архитектурных схем реальному коду;
- демонстрация только успешных пользовательских сценариев;
- отсутствие выводов по результатам тестирования.

---

## ⚜️ Ограничения по содержанию практической части

Курсовая работа должна иметь **защитную направленность**.

Допускается создание локальных учебных примеров уязвимостей, если они нужны для проверки собственной защиты и запускаются только в контролируемой среде.

Основным результатом курсовой работы не должны быть:

- программы-вымогатели;
- кейлоггеры;
- шпионское ПО;
- средства скрытого удалённого управления;
- ботнеты;
- инструменты проведения DDoS-атак;
- фишинговые сервисы;
- средства эксплуатации сторонних систем.

Если в работе исследуется уязвимость, проверка проводится только на собственной программе или специально созданном учебном стенде.

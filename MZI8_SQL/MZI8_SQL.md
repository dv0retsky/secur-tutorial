# Практическое занятие 8: SQL Injection и безопасная работа с базой данных

## 1. Зачем веб-приложению база данных

Практически любое современное веб-приложение должно хранить информацию между запросами пользователя. В интернет-магазине это сведения о товарах, заказах и покупателях, в социальной сети — аккаунты и публикации, в банковском приложении — пользователи, балансы и история операций.

**База данных** — это организованная система хранения информации, позволяющая добавлять, изменять, удалять и быстро находить данные. В отличие от обычного набора файлов база данных рассчитана на одновременную работу множества пользователей и поддерживает связи между сущностями.

В учебном приложении  [**MiniBank**](https://github.com/malkursk/stepik_minibank) можно представить таблицу пользователей следующим образом:

| id | username | email | password | is_admin |
|---:|----------|-------|----------|---------:|
| 1 | alice | alice@example.com | pass123 | 0 |
| 2 | bob | bob@example.com | qwerty | 0 |
| 3 | admin | admin@example.com | secret99 | 1 |

Здесь каждая строка соответствует отдельному пользователю, а столбцы задают свойства пользователя.

Основные термины:

- **таблица** — набор однотипных записей;
- **строка** (`row`, `record`) — отдельная запись;
- **столбец** (`column`) — отдельный атрибут записи;
- **первичный ключ** (`primary key`) — уникальный идентификатор строки.

Для работы с реляционными базами данных используется язык **SQL — Structured Query Language**.

---

## 2. Основные SQL-команды

SQL позволяет выполнять четыре базовые операции над данными: чтение, добавление, изменение и удаление. Совместно их часто называют **CRUD**: Create, Read, Update, Delete.

### 2.1. SELECT — чтение данных

Общий вид:

```sql
SELECT столбцы
FROM таблица
WHERE условие;
```

Например, выбрать всех пользователей:

```sql
SELECT * FROM users;
```

Выбрать только логины:

```sql
SELECT username FROM users;
```

Найти конкретного пользователя:

```sql
SELECT *
FROM users
WHERE username = 'alice';
```

Фильтрация выполняется выражением `WHERE`. В нём могут применяться операторы сравнения и логические операции `AND`, `OR`, `NOT`.

Пример проверки пары логин/пароль:

```sql
SELECT *
FROM users
WHERE username = 'alice'
  AND password = 'pass123';
```

Именно запрос подобного вида часто лежит в основе примитивной проверки логина и пароля.

### 2.2. INSERT — добавление данных

```sql
INSERT INTO users (username, email, password, is_admin)
VALUES ('charlie', 'charlie@example.com', 'mypass', 0);
```

### 2.3. UPDATE — изменение данных

```sql
UPDATE users
SET password = 'newpass456'
WHERE username = 'alice';
```

Особенно важно помнить о `WHERE`. Если выполнить:

```sql
UPDATE users
SET is_admin = 1;
```

то значение будет изменено **у всех строк** таблицы.

### 2.4. DELETE — удаление данных

```sql
DELETE FROM users
WHERE username = 'charlie';
```

Команда

```sql
DELETE FROM users;
```

удалит все строки таблицы. Поэтому в реальных информационных системах изменение и удаление данных должны выполняться с особой осторожностью и с минимально необходимыми правами учётной записи БД.

## 3. Как приложение формирует SQL-запрос

Рассмотрим упрощённую форму авторизации. Пользователь вводит логин и пароль, после чего приложение должно проверить, существует ли такая пара в базе данных.

Небезопасная реализация на Python может выглядеть следующим образом:

```python
username = request.form.get("username", "")
password = request.form.get("password", "")

query = (
    f"SELECT * FROM users "
    f"WHERE username='{username}' "
    f"AND password='{password}'"
)

cursor.execute(query)
user = cursor.fetchone()
```

Если введены:

```text
username: alice
password: pass123
```

приложение сформирует:

```sql
SELECT *
FROM users
WHERE username='alice'
  AND password='pass123';
```

Проблема начинается тогда, когда пользовательский ввод содержит символы, которые SQL-интерпретатор воспринимает не как обычные данные, а как часть SQL-команды.

---

## 4. Что такое SQL Injection

**SQL Injection** — класс уязвимостей, возникающий тогда, когда данные, полученные от пользователя, небезопасно объединяются со строкой SQL-запроса.

Ключевая причина уязвимости — смешение двух разных сущностей:

```text
структура SQL-запроса
+
пользовательские данные
```

Если они объединяются строковой конкатенацией или форматированием, пользователь может попытаться изменить не только значение параметра, но и **саму логику запроса**.

---

## 5. Почему SQL Injection опасна

Последствия зависят от того, какие запросы выполняет приложение и какие права имеет его учётная запись в базе данных. SQL Injection может приводить к обходу проверки логина и пароля, чтению закрытых данных, изменению или удалению записей, получению административных прав на уровне приложения и раскрытию структуры базы.

Важно понимать: опасность заключается не в конкретной строке ввода, а в том, что **внешние данные начинают управлять структурой SQL**.

## 7. Исследование уязвимого входа

Рассмотрим фрагмент обработчика `/login`:

```python
@app.route('/login', methods=['POST'])
def login():
    username = request.form.get('username', '')
    password = request.form.get('password', '')

    query = (
        f"SELECT * FROM users "
        f"WHERE username='{username}' "
        f"AND password='{password}'"
    )

    cursor.execute(query)
    user = cursor.fetchone()
```

Критическая операция — непосредственная подстановка `username` и `password` в SQL-текст.

### 7.1. Нормальный сценарий

Введите:

```text
Логин: alice
Пароль: pass123
```

Запрос соответствует намерению разработчика:

```sql
SELECT *
FROM users
WHERE username='alice'
  AND password='pass123';
```

### 7.2. Изменение логики выражения

В учебном приложении попробуйте в поле логина ввести:

```text
admin' OR '1'='1'--
```

Пароль может быть произвольным.

После подстановки часть пользовательского ввода становится SQL-синтаксисом. В результате условие `WHERE` может измениться.

Обратите внимание на цепочку:

```text
ввод пользователя
        ↓
вставка в SQL-строку
        ↓
SQL-парсер воспринимает часть ввода как код
        ↓
меняется логика WHERE
```

Если вход становится возможен без правильного пароля, приложение уязвимо.

## 8. Основная защита: параметризованные запросы

Правильный способ — передать структуру запроса и значения параметров **раздельно**.

Для SQLite:

```python
query = """
SELECT *
FROM users
WHERE username = ?
  AND password = ?
"""

cursor.execute(query, (username, password))
```

Теперь даже строка, содержащая кавычки и SQL-операторы, передаётся в СУБД как **значение параметра**, а не как часть кода.

Упрощённо:

```text
SQL-код:
SELECT * FROM users WHERE username=? AND password=?

Параметры:
username = "admin' OR '1'='1'--"
password = "anything"
```

## 9. Исправление MiniBank

Замените уязвимый обработчик входа на параметризованный запрос:

```python
@app.route('/login', methods=['GET', 'POST'])
def login():
    if request.method == 'POST':
        username = request.form.get('username', '')
        password = request.form.get('password', '')

        query = """
        SELECT *
        FROM users
        WHERE username=?
          AND password=?
        """

        conn = get_db()
        cursor = conn.cursor()
        cursor.execute(query, (username, password))
        user = cursor.fetchone()
        conn.close()

        if user:
            session['username'] = user['username']
            return redirect(url_for('guestbook'))

        return render_template(
            'login.html',
            error='Неверный логин или пароль'
        )

    return render_template('login.html')
```

Перезапустите приложение:

```bash
python app.py
```

Повторите прежнюю проверку. Ожидаемый результат:

```text
Неверный логин или пароль
```

Это обязательная часть работы: после исправления нужно повторить исходный тест и убедиться, что уязвимость действительно устранена.

## 10. ORM и SQL Injection

**ORM (Object-Relational Mapping)** сопоставляет таблицы базы данных объектам языка программирования.

Например:

```python
class User(db.Model):
    id = db.Column(db.Integer, primary_key=True)
    username = db.Column(db.String(50), unique=True)
    password = db.Column(db.String(100))
    is_admin = db.Column(db.Boolean, default=False)
```

Поиск пользователя:

```python
user = User.query.filter_by(username=username).first()
```

ORM обычно формирует параметризованный SQL автоматически. Но ORM не является «магической защитой»: если разработчик вручную собирает SQL-строку с пользовательским вводом, SQL Injection может появиться снова.

## 11. Дополнительные уровни защиты

Параметризация — основной и обязательный механизм, но полезны и дополнительные меры.

**Валидация данных.** Если логин должен состоять только из букв, цифр и `_`, это можно проверить заранее. Однако валидация не заменяет параметризованный запрос.

**Минимальные привилегии.** Веб-приложение не должно подключаться к БД под суперпользователем. Нужно выдавать только те права, которые требуются для работы.

**Безопасные ошибки.** Пользователю не следует показывать полный текст исключения СУБД, раскрывающий структуру запросов и тип базы.

**Хеширование паролей.** В учебной БД пароли могут храниться открыто ради наглядности. В реальной системе применяются алгоритмы хеширования паролей с солью, например Argon2id, bcrypt или scrypt.

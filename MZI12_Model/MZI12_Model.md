# Практическое занятие №12: Модель угроз и требования к защите информации

## 1. Модель нарушителя

**Модель нарушителя** — описание лица или процесса, способного нарушить безопасность системы.

Необходимо определить:

- имеет ли нарушитель легитимную учётную запись;
- к каким интерфейсам имеет доступ;
- может ли изменять пользовательский ввод;
- может ли наблюдать сетевой трафик;
- располагает ли копией БД;
- имеет ли физический доступ к устройству.

Пример:

> В работе рассматривается внешний нарушитель, имеющий сетевой доступ к веб-интерфейсу приложения, но не имеющий административной учётной записи и прямого доступа к серверу. Нарушитель способен изменять параметры запросов и отправлять специально сформированный пользовательский ввод.

## 2. Угроза, уязвимость и атака

**Угроза** — потенциальная возможность нарушения безопасности.

**Уязвимость** — слабое место системы.

**Атака** — конкретная попытка использовать уязвимость.

Пример:

```text
Угроза:
несанкционированный доступ к данным

Уязвимость:
сервер не проверяет владельца объекта

Атака:
пользователь изменяет id объекта в запросе

Последствие:
получение чужих данных

Защита:
серверная проверка прав доступа
```

## 3. Формирование перечня угроз

Для курсовой работы рекомендуется определить не менее пяти содержательных угроз. Они должны вытекать из архитектуры проекта, а не выбираться из общего списка случайным образом.

Возможные категории: компрометация учётных данных, обход аутентификации, нарушение авторизации, утечка данных, подмена данных, внедрение пользовательского кода, компрометация сессии, отсутствие контроля целостности.

## 5. Требования безопасности

Требование должно быть проверяемым.

Плохо:

> Система должна быть защищена от SQL Injection.

Лучше:

> SQL-запросы, содержащие пользовательские данные, должны выполняться с использованием параметризованных запросов без конкатенации пользовательского ввода со строкой SQL.

## 6. Функциональные требования и требования безопасности

Функциональные требования описывают возможности системы:

```text
FR-01 — пользователь может зарегистрироваться.
FR-02 — пользователь может войти в систему.
FR-03 — пользователь может создать объект.
```

Требования безопасности описывают защитные свойства:

```text
SEC-01 — пароль не хранится в открытом виде.
SEC-02 — пользователь не получает доступ к чужим объектам.
SEC-03 — пользовательский ввод не изменяет структуру SQL-запроса.
SEC-04 — пользовательский HTML не выполняется в браузере.
```

## 7. Выбор методов защиты

Каждый метод должен быть связан с конкретной угрозой.

| Угроза | Метод защиты |
|---|---|
| Компрометация БД с паролями | Argon2id / bcrypt / scrypt |
| SQL Injection | Параметризованные запросы |
| XSS | Контекстное экранирование + CSP |
| CSRF | CSRF-токены + SameSite |
| Доступ к чужим объектам | Серверная авторизация |
| Изменение защищённого файла | AEAD / MAC |

## 8. Принцип многоуровневой защиты

**Defense in Depth** предполагает использование нескольких взаимодополняющих механизмов.

Например:

```text
валидация ввода
+
параметризованные запросы
+
экранирование HTML
+
CSP
+
безопасные cookie
+
контроль доступа
+
журналирование
```

## 9. Архитектура с механизмами защиты

Схему предыдущей недели следует дополнить:

```text
Пользователь
     │
     │ недоверенный ввод
     ▼
Приложение
 ├─ аутентификация
 ├─ авторизация
 ├─ валидация
 ├─ экранирование
 └─ журналирование
     │
     │ параметризованные запросы
     ▼
Хранилище
```

## 10. План проверки защиты

| ID | Требование | Проверка | Ожидаемый результат |
|---|---|---|---|
| SEC-01 | Пароль не хранится открыто | Просмотр БД | Открытый пароль отсутствует |
| SEC-02 | Нет доступа к чужим объектам | Изменение id | Доступ запрещён |
| SEC-03 | SQL Injection не меняет запрос | Специальный ввод | Обрабатывается как данные |

## 11. Практическая работа на занятии

Необходимо:

1. сформировать модель нарушителя;
2. определить не менее пяти угроз;
3. сформулировать требования безопасности;
4. выбрать методы защиты;
5. дополнить архитектурную схему;
6. составить предварительный план тестирования.

# Практическое занятие №4: Применение криптографии

# 🕹️ Криптография как часть реальной информационной системы

На предыдущем занятии криптографические алгоритмы рассматривались как отдельные примитивы: шифрование, хеширование, цифровая подпись, выработка общего секрета. На практике эти механизмы почти никогда не используются изолированно.

Рассмотрим обычное открытие сайта по HTTPS. Браузеру необходимо подтвердить подлинность сервера, согласовать с ним общий секрет, получить сеансовые ключи, зашифровать дальнейший трафик и обнаруживать попытки его изменения. Для этого одновременно используются сертификаты X.509, цифровая подпись, механизмы обмена ключами, функции выработки ключей и симметричное аутентифицированное шифрование.

Именно поэтому при проектировании защищённой системы важно понимать не только отдельный алгоритм, но и то, как несколько криптографических примитивов взаимодействуют между собой.

---

# 🕹️ AES — Advanced Encryption Standard

**AES (Advanced Encryption Standard)** — современный симметричный блочный шифр, широко используемый для защиты данных. AES пришёл на смену DES, ключевое пространство которого стало недостаточным для современных вычислительных возможностей.

Основные параметры AES:

| Параметр | Значение |
|---|---|
| Размер блока | 128 бит |
| AES-128 | ключ 128 бит, 10 раундов |
| AES-192 | ключ 192 бита, 12 раундов |
| AES-256 | ключ 256 бит, 14 раундов |

Важно различать **размер блока** и **размер ключа**. Независимо от того, используется AES-128, AES-192 или AES-256, размер обрабатываемого блока всегда составляет 128 бит, то есть 16 байт. Меняется длина ключа и количество раундов.

---

# 🕹️ Что означает «блочный шифр»

AES не шифрует произвольный текст «целиком». Базовая операция принимает ровно один 128-битный блок:

```text
16 байт открытого текста
          |
          | ключ
          v
         AES
          |
          v
16 байт шифротекста
```

Если требуется защитить файл размером несколько мегабайт, данные должны обрабатываться в соответствии с определённым **режимом работы**. Поэтому в прикладной системе фактически используется не просто AES, а конструкция вроде AES-GCM, AES-CTR или AES-CBC.

Режим определяет, как отдельные блоки связаны между собой, каким образом используется nonce или IV и обеспечивается ли проверка целостности. Для новых приложений предпочтительнее применять аутентифицированное шифрование, например AES-GCM.

---

# 🕹️ Состояние AES

Внутри AES один блок из 16 байт представляется как структура `State`, которую обычно изображают матрицей 4×4:

```text
| b0  b4  b8  b12 |
| b1  b5  b9  b13 |
| b2  b6  b10 b14 |
| b3  b7  b11 b15 |
```

Спецификация AES рассматривает байты по столбцам, а не как простое построчное размещение текста. Это важная деталь, которую следует учитывать при ручном разборе алгоритма.

Каждый раунд AES преобразует состояние последовательностью операций.

---

# 🕹️ Структура AES

Для AES-128 общая схема имеет вид:

```text
Исходный блок
      |
      v
AddRoundKey
      |
      v
Раунд 1:
SubBytes
ShiftRows
MixColumns
AddRoundKey
      |
      v
...
      |
      v
Раунд 9:
SubBytes
ShiftRows
MixColumns
AddRoundKey
      |
      v
Финальный раунд:
SubBytes
ShiftRows
AddRoundKey
      |
      v
Шифротекст
```

Финальный раунд отличается тем, что операция `MixColumns` в нём не выполняется.

---

# 🕹️ AddRoundKey

**AddRoundKey** — операция, при которой состояние AES объединяется с раундовым ключом при помощи XOR.

```text
State XOR RoundKey -> New State
```

Операция XOR имеет свойства:

```text
0 XOR 0 = 0
0 XOR 1 = 1
1 XOR 0 = 1
1 XOR 1 = 0
```

и:

```text
A XOR B XOR B = A
```

Однако стойкость AES не строится только на XOR. Если бы алгоритм состоял лишь из XOR с повторяющимся ключом, такая схема была бы уязвима. Безопасность формируется совокупностью нелинейных и линейных преобразований в нескольких раундах.

---

# 🕹️ Расширение ключа

AES не использует исходный ключ в неизменном виде во всех раундах. С помощью процедуры **Key Expansion** из него формируется набор раундовых ключей.

Критически важно понимать, что ключ AES нельзя получать простым повторением короткого слова. Например:

```text
KEYSKEYSKEYSKEYS
```

формально имеет длину 16 байт, но не обладает энтропией случайного 128-битного ключа.

Для реального ключа следует использовать криптографически стойкую генерацию:

```python
import secrets

key = secrets.token_bytes(32)
```

Если ключ должен выводиться из парольной фразы, применяется KDF.

---

# 🕹️ SubBytes

**SubBytes** — нелинейное преобразование, при котором каждый байт состояния заменяется другим байтом согласно фиксированной таблице S-box.

S-box AES построен не случайно: его значения получены с помощью операций над конечным полем и аффинного преобразования.

Главная роль `SubBytes` — создать нелинейность. Если бы весь шифр состоял только из линейных операций, связь между открытым текстом, ключом и шифротекстом можно было бы выразить значительно проще.

---

# 🕹️ ShiftRows

**ShiftRows** выполняет циклический сдвиг строк состояния:

```text
строка 0: сдвиг 0
строка 1: сдвиг 1 байт влево
строка 2: сдвиг 2 байта влево
строка 3: сдвиг 3 байта влево
```

Эта операция перераспределяет байты между столбцами и способствует диффузии — распространению влияния отдельных входных битов по всему блоку.

---

# 🕹️ MixColumns

**MixColumns** преобразует каждый столбец состояния с использованием арифметики конечного поля GF(2^8).

Каждый столбец умножается на фиксированную матрицу:

```text
| 2 3 1 1 |
| 1 2 3 1 |
| 1 1 2 3 |
| 3 1 1 2 |
```

Обычное целочисленное умножение здесь не используется. Главная задача MixColumns — распространить влияние каждого входного байта на несколько выходных байтов.

---

# 🕹️ Confusion и diffusion

При объяснении блочных шифров используют понятия Клода Шеннона.

**Confusion — запутывание.** Связь между ключом и шифротекстом должна быть сложной и нелинейной.

**Diffusion — рассеивание.** Статистическая структура открытого текста должна распределяться по большому количеству битов шифротекста.

Упрощённо:

```text
SubBytes            -> нелинейность
ShiftRows/MixColumns -> диффузия
AddRoundKey          -> связь с секретным ключом
```

Безопасность AES формируется всей раундовой конструкцией, а не одной отдельной операцией.

---

# 🕹️ Почему AES считается стойким

Стойкость AES определяется большим пространством ключей, продуманной раундовой структурой и многолетним публичным криптоанализом.

Для AES-128 существует:

```text
2^128 ≈ 3,4 × 10^38
```

возможных ключей.

Для AES-256:

```text
2^256 ≈ 1,16 × 10^77
```

вариантов.

Однако утверждение «AES невозможно взломать» некорректно. Реальная система может быть скомпрометирована через кражу ключа, слабый пароль, повтор nonce, ошибку реализации, побочный канал или неправильный режим работы.

---

# 🕹️ Ключ из пароля

Пользователь обычно не способен запомнить случайный 256-битный ключ. Поэтому в системах шифрования файлов часто используется парольная фраза.

Напрямую применять пароль как AES-ключ нельзя.

Необходима **KDF (Key Derivation Function)**:

```text
Пароль + Salt
     |
     v
    KDF
     |
     v
AES-ключ
```

Для парольных сценариев применяются, например, Argon2id, scrypt или PBKDF2.

---

# 🕹️ AES-GCM

**AES-GCM (Galois/Counter Mode)** относится к AEAD-конструкциям и обеспечивает одновременно конфиденциальность, контроль целостности и аутентичность шифротекста.

```text
AES-GCM(
    key,
    nonce,
    plaintext,
    associated_data
)
        |
        v
ciphertext + authentication tag
```

Если злоумышленник изменит шифротекст, тег перестанет проходить проверку.

Критическое правило:

> одно и то же значение nonce нельзя повторно использовать с одним и тем же ключом.

В AES-GCM часто используется 96-битный nonce, то есть 12 байт. Nonce не обязан быть секретным.

**AAD (Associated Data)** — данные, которые не шифруются, но включаются в проверку целостности.

---

# 🕹️ Цифровая подпись

**Цифровая подпись** — криптографический механизм, позволяющий проверить целостность сообщения и подтвердить, что подпись сформирована с использованием соответствующего закрытого ключа.

Для подписи используется пара ключей:

```text
закрытый ключ sk
открытый ключ pk
```

Закрытый ключ должен оставаться у владельца, открытый может распространяться среди проверяющих.

```text
Подписывающий:
документ + sk -> подпись

Проверяющий:
документ + подпись + pk -> корректна / некорректна
```

Цифровая подпись не является шифрованием и не обеспечивает конфиденциальность документа.

---

# 🕹️ Формальная схема цифровой подписи

Абстрактная схема состоит из трёх алгоритмов.

```text
(sk, pk) <- KeyGen()
signature <- Sign(message, sk)
Verify(message, signature, pk) -> true/false
```

Если документ изменён после подписания, проверка должна завершиться неуспешно.

В реальных системах обычно подписывается хеш или специальным образом подготовленное представление документа, поскольку документы могут иметь произвольный размер.

---

# 🕹️ Подпись и шифрование — разные операции

Цифровую подпись иногда объясняют как «шифрование закрытым ключом». Для современной криптографии это слишком грубое и часто ошибочное объяснение.

Например, ECDSA, Ed25519 и ГОСТ Р 34.10-2012 не являются алгоритмами шифрования.

Корректная модель:

```text
Sign(message, private_key)
Verify(message, signature, public_key)
```

а не:

```text
Encrypt(message, private_key)
```

Подпись нельзя «расшифровать» и получить из неё исходный документ.

---

# 🕹️ Алгоритмы цифровой подписи

**RSA-PSS** — современная схема подписи на основе RSA. Она широко поддерживается и используется в существующей инфраструктуре.

**ECDSA** — алгоритм цифровой подписи на эллиптических кривых. Он обеспечивает высокий уровень стойкости при сравнительно небольшом размере ключей.

**Ed25519** — современный алгоритм подписи, спроектированный с акцентом на безопасную и удобную реализацию.

**ГОСТ Р 34.10-2012** — российский алгоритм электронной цифровой подписи на эллиптических кривых.

---

# 🕹️ Где используется цифровая подпись

Цифровая подпись применяется не только в электронном документообороте. Она используется для подписи программных обновлений, установочных пакетов, Git-коммитов и тегов, прошивок оборудования, сертификатов и различных объектов инфраструктуры доверия.

Например:

```text
update.bin
     |
     | Sign(private_key)
     v
update.bin + signature
```

Перед установкой клиент проверяет подпись открытым ключом разработчика. Если файл был изменён после подписания, проверка завершится ошибкой.

---

# 🕹️ OpenPGP и GPG

**OpenPGP** — стандарт форматов и криптографических механизмов для шифрования и цифровой подписи данных.

**GnuPG (GPG)** — свободная реализация OpenPGP.

Пример:

```bash
gpg --full-generate-key
gpg --detach-sign document.txt
gpg --verify document.txt.sig document.txt
```

При этом доверие к открытому ключу остаётся отдельной задачей. Если файл, подпись и неизвестный публичный ключ скачаны из одного недоверенного источника, это ещё не доказывает, кому принадлежит ключ.

Эту проблему в веб-инфраструктуре решает PKI.


# 🕹️ PKI — инфраструктура открытых ключей

**PKI (Public Key Infrastructure)** — совокупность технических и организационных механизмов, предназначенных для управления открытыми ключами, сертификатами и доверием между участниками.

Главная проблема, которую решает PKI:

> как проверить, что определённый открытый ключ действительно принадлежит нужному серверу или субъекту?

Если браузер просто получил от сервера открытый ключ, злоумышленник мог бы попытаться подменить его своим. Поэтому используется цифровой сертификат, подписанный доверенной стороной.

---

# 🕹️ Сертификат X.509

**X.509** — широко используемый стандарт формата цифровых сертификатов.

Сертификат связывает открытый ключ с набором идентификационных данных и содержит цифровую подпись издателя.

Типичный сертификат включает:

```text
версию
серийный номер
издателя
период действия
данные субъекта
открытый ключ
расширения
алгоритм подписи
подпись удостоверяющего центра
```

Для веб-сайтов особенно важно расширение **Subject Alternative Name (SAN)**, где указываются доменные имена, для которых сертификат считается действительным.

Сертификат не содержит закрытый ключ сервера. Закрытый ключ должен оставаться на сервере или в защищённом хранилище.

---

# 🕹️ Удостоверяющий центр

**CA (Certification Authority)** — удостоверяющий центр, который подписывает сертификаты и подтверждает связь между открытым ключом и определённым именем или субъектом в рамках своей политики.

Упрощённо:

```text
Сайт генерирует пару ключей
        |
        v
открытый ключ + доменное имя
        |
        v
проверка CA
        |
        v
сертификат
        |
        v
подпись CA
```

Браузер доверяет не «любому сертификату», а сертификату, который удалось связать с доверенной точкой через проверяемую цепочку.

---

# 🕹️ Цепочка сертификатов

Обычно конечный сертификат сайта не подписывается непосредственно корневым CA.

Используется цепочка:

```text
Root CA
   |
   v
Intermediate CA
   |
   v
End-Entity Certificate
```

**Root CA** — корневой удостоверяющий центр. Его сертификат является точкой доверия и находится в доверенном хранилище операционной системы или браузера.

**Intermediate CA** — промежуточный удостоверяющий центр, подписанный корневым или другим промежуточным CA.

**End-Entity Certificate** — сертификат конкретного сайта, пользователя или сервиса.

Такое разделение позволяет не использовать корневой закрытый ключ для повседневной выдачи конечных сертификатов.

---

# 🕹️ Как браузер проверяет сертификат

При HTTPS-подключении браузер выполняет несколько проверок.

Упрощённо:

```text
1. Получить сертификат сервера
2. Проверить период действия
3. Проверить доменное имя
4. Проверить цифровую подпись издателя
5. Построить цепочку до доверенного Root CA
6. Проверить ограничения сертификатов
7. Учесть сведения об отзыве, если применимо
```

Если проверка цепочки не завершается доверенной точкой, браузер показывает предупреждение.

Это не означает, что математически невозможно установить зашифрованное соединение. Это означает, что браузер не смог подтвердить, что предъявленный открытый ключ действительно относится к нужному серверу.

---

# 🕹️ Самоподписанный сертификат

**Самоподписанный сертификат** подписан тем же закрытым ключом, которому соответствует содержащийся в сертификате открытый ключ.

Такой сертификат может использоваться для шифрования, но браузер не будет доверять ему автоматически.

Самоподписанные сертификаты применимы:

- в лабораторных стендах;
- во внутренних инфраструктурах;
- при тестировании;
- в закрытых системах с собственным механизмом распределения доверия.

Для публичного сайта пользователю не следует предлагать просто игнорировать предупреждение браузера. В публичной системе должна быть настроена корректная цепочка доверия.

---

# 🕹️ Срок действия и отзыв сертификата

Сертификаты имеют ограниченный период действия. После его окончания сертификат не должен считаться действительным.

Но закрытый ключ может быть скомпрометирован и до истечения срока. Поэтому существуют механизмы отзыва.

Классические механизмы:

- **CRL** — список отозванных сертификатов;
- **OCSP** — протокол запроса статуса сертификата.

На практике отзыв является лишь одним элементом управления сертификатами. Важны также короткие сроки действия, автоматизация перевыпуска, защищённое хранение ключей и корректная реакция на компрометацию.

# 🕹️ HTTPS и TLS

**HTTPS** — это использование HTTP поверх защищённого канала TLS.

Упрощённо:

```text
HTTP
  |
  v
TLS
  |
  v
TCP
  |
  v
IP
```

Для HTTP/3 транспортная схема отличается, но для понимания базовой модели удобно начинать с классического стека HTTP + TLS + TCP.

**TLS (Transport Layer Security)** обеспечивает:

- конфиденциальность передаваемых данных;
- контроль целостности;
- аутентификацию сервера;
- при необходимости аутентификацию клиента.

---

# 🕹️ Что защищает HTTPS

При корректно установленном TLS-соединении наблюдатель на пути не должен иметь возможности прочитать содержимое HTTP-запросов и ответов.

Защищаются, например:

```text
Cookie
Authorization
POST body
содержимое ответа
```

Однако HTTPS не скрывает абсолютно всю информацию о сетевом соединении. Сетевые участники по-прежнему могут наблюдать IP-адреса, объём трафика, время соединения и часть метаданных.

Поэтому HTTPS следует понимать как защиту канала, а не как полную анонимизацию сетевой активности.

---

# 🕹️ TLS 1.3: общая идея handshake

Современный процесс установления TLS-соединения удобно рассматривать на примере TLS 1.3.

Упрощённая последовательность:

```text
Клиент                         Сервер
  |                              |
  | ---- ClientHello ----------> |
  |                              |
  | <--- ServerHello ----------- |
  | <--- Certificate ----------- |
  | <--- CertificateVerify ----- |
  | <--- Finished -------------- |
  |                              |
  | ---- Finished -------------> |
  |                              |
  | ==== защищённые данные ===== |
```

Реальный протокол содержит дополнительные детали и расширения, но эта схема хорошо показывает основные этапы.

---

# 🕹️ ClientHello и ServerHello

В `ClientHello` клиент сообщает поддерживаемые параметры и отправляет данные, необходимые для согласования ключевого материала.

Сервер отвечает `ServerHello`, выбирая совместимые параметры соединения.

В современных версиях TLS выбор алгоритмов больше не следует представлять как единственную «монолитную» строку, описывающую сразу обмен ключами, подпись, шифрование и хеш. Разные задачи согласуются отдельными механизмами.

---

# 🕹️ Согласование общего секрета

В современных TLS-соединениях широко используется эфемерный ECDHE.

Упрощённо:

```text
Клиент                         Сервер
  |                              |
  | ---- ephemeral public -----> |
  | <--- ephemeral public ------ |
  |                              |
  | вычисляет shared secret      |
  |                shared secret |
```

Сам общий секрет напрямую по сети не передаётся.

Из него с помощью функций выработки ключей формируются сеансовые ключи, используемые далее для защиты трафика.

---

# 🕹️ Forward Secrecy

Использование эфемерных ключей позволяет получить свойство **forward secrecy** — прямую секретность.

Его смысл заключается в том, что последующая компрометация долговременного закрытого ключа сервера не должна автоматически позволить расшифровать ранее записанные TLS-сессии.

Сеансовые ключи формируются с участием временных секретов, которые не используются повторно после завершения соединения.

---

# 🕹️ Аутентификация сервера в TLS

Если две стороны просто выполнят ECDHE без аутентификации, злоумышленник сможет попытаться установить отдельный секрет с каждой стороной.

Поэтому сервер доказывает владение закрытым ключом, соответствующим сертификату.

Браузер:

1. проверяет сертификат;
2. убеждается, что доменное имя соответствует SAN;
3. проверяет цепочку доверия;
4. проверяет цифровую подпись сервером данных handshake.

Таким образом, TLS соединяет две задачи:

```text
выработка общего секрета
        +
аутентификация сервера
```

---

# 🕹️ Сеансовое шифрование в TLS

После завершения handshake основная передача данных выполняется быстрыми симметричными AEAD-алгоритмами.

Примеры:

```text
AES-GCM
ChaCha20-Poly1305
```

Это и есть практический гибридный подход:

```text
асимметрические механизмы
        |
        +--> аутентификация и согласование ключей

симметрические механизмы
        |
        +--> защита основного потока данных
```

---

# 🕹️ Что HTTPS не исправляет

HTTPS защищает канал связи, но не устраняет ошибки самого приложения.

Например, HTTPS не предотвращает:

- SQL Injection;
- XSS;
- слабые пароли;
- ошибочную авторизацию;
- заражение компьютера;
- компрометацию сервера;
- утечку базы данных;
- фишинг на другом домене.

Значок защищённого соединения означает, что соединение с указанным доменом прошло криптографическую проверку. Он не означает, что содержимое сайта обязательно безопасно или заслуживает доверия.

# 🕹️ Типовые ошибки при применении криптографии

## 37.1. Самодельная генерация ключа

Плохо:

```python
key = b"passwordpassword"
```

Правильнее использовать криптографический генератор или KDF.

## 37.2. Повтор nonce в AES-GCM

Пара:

```text
(key, nonce)
```

не должна повторяться для разных сообщений.

## 37.3. Шифрование без контроля целостности

Шифротекст должен не только скрывать содержимое, но и позволять обнаруживать модификацию.

## 37.4. Хранение закрытого ключа в репозитории

Закрытые ключи TLS и подписи нельзя помещать в публичные Git-репозитории. Если секрет был опубликован, его необходимо считать скомпрометированным и заменить.

## 37.5. Игнорирование ошибок сертификата

Предупреждение браузера может указывать на неправильное имя, истёкший сертификат, проблему цепочки или реальную попытку перехвата.

## Задание 1. AES-GCM: шифрование и расшифрование сообщения

Создайте файл `aes_gcm_demo.py`:

```python
import os
from cryptography.hazmat.primitives.ciphers.aead import AESGCM


def encrypt_message(message: bytes) -> tuple[bytes, bytes, bytes]:
    key = AESGCM.generate_key(bit_length=256)
    nonce = os.urandom(12)

    aesgcm = AESGCM(key)
    ciphertext = aesgcm.encrypt(
        nonce,
        message,
        None
    )

    return key, nonce, ciphertext


def decrypt_message(
    key: bytes,
    nonce: bytes,
    ciphertext: bytes
) -> bytes:
    aesgcm = AESGCM(key)

    return aesgcm.decrypt(
        nonce,
        ciphertext,
        None
    )


message = "Практическое занятие по криптографии".encode("utf-8")

key, nonce, ciphertext = encrypt_message(message)
plaintext = decrypt_message(key, nonce, ciphertext)

print("Ключ:", key.hex())
print("Nonce:", nonce.hex())
print("Шифротекст:", ciphertext.hex())
print("Расшифрованный текст:", plaintext.decode("utf-8"))
```

```python
import os
from cryptography.exceptions import InvalidTag
from cryptography.hazmat.primitives.ciphers.aead import AESGCM


key = AESGCM.generate_key(bit_length=256)
nonce = os.urandom(12)
message = b"Transfer amount: 1000"

ciphertext = aesgcm.encrypt(
    nonce,
    message,
    b"transaction-v1"
)

tampered = bytearray(ciphertext)
tampered[0] ^= 1

try:
    result = aesgcm.decrypt(

except InvalidTag:
```

## Задание 3. Шифрование файла

```python
import os
from pathlib import Path
from cryptography.hazmat.primitives.ciphers.aead import AESGCM


SOURCE_FILE = Path("document.txt")
ENCRYPTED_FILE = Path("document.enc")
DECRYPTED_FILE = Path("document.dec.txt")
KEY_FILE = Path("document.key")


if not SOURCE_FILE.exists():
    SOURCE_FILE.write_text(
        "Методы защиты информации\n"
        "Применение криптографии\n",
        encoding="utf-8"
    )


key = AESGCM.generate_key(bit_length=256)
nonce = os.urandom(12)

plaintext = SOURCE_FILE.read_bytes()

aesgcm = AESGCM(key)

ciphertext = aesgcm.encrypt(
    nonce,
    plaintext,
    SOURCE_FILE.name.encode("utf-8")
)

ENCRYPTED_FILE.write_bytes(nonce + ciphertext)
KEY_FILE.write_bytes(key)

stored = ENCRYPTED_FILE.read_bytes()
stored_nonce = stored[:12]
stored_ciphertext = stored[12:]

decrypted = AESGCM(KEY_FILE.read_bytes()).decrypt(
    stored_nonce,
    stored_ciphertext,
    SOURCE_FILE.name.encode("utf-8")
)

DECRYPTED_FILE.write_bytes(decrypted)

print("Исходный файл:", SOURCE_FILE)
print("Зашифрованный файл:", ENCRYPTED_FILE)
print("Расшифрованный файл:", DECRYPTED_FILE)
print("Совпадение:", plaintext == decrypted)
```

```python
    Ed25519PrivateKey
)
```

```python
public_key = private_key.public_key()

private_pem = private_key.private_bytes(
    encoding=serialization.Encoding.PEM,
    format=serialization.PrivateFormat.PKCS8,
    encryption_algorithm=serialization.BestAvailableEncryption(
        b"Strong-Lab-Password-2026"

    encoding=serialization.Encoding.PEM,
    format=serialization.PublicFormat.SubjectPublicKeyInfo
)

with open("private_key.pem", "wb") as file:
    file.write(private_pem)

with open("public_key.pem", "wb") as file:

print("Созданы:")
```
